# Project Control Center

Стартовый веб-dashboard для университетского проекта: обзор проекта, KPI задач, четыре и более подгрупп, вклад отдельных участников, реестр людей и руководителей, задачи, проблемы и решения.

## Что уже работает в демо-режиме

- Добавление, редактирование и удаление подгрупп.
- Добавление, редактирование и удаление участников и руководителей.
- Добавление, редактирование и удаление задач, назначение ответственного, дедлайн, статус и вес задачи.
- Кольцевая диаграмма каждой подгруппы: каждому участнику соответствует отдельный сектор, размер сектора пропорционален назначенному объёму задач, заполненная цветом часть отражает личный прогресс; число в центре — прогресс группы. Участнику можно задать ручной личный процент.
- Общий прогресс проекта рассчитывается по задачам автоматически. В настройках можно переключить его на ручной процент.
- Добавление, редактирование и удаление проблем, фиксация решения и статуса.
- Последняя активность.
- Фильтр участников по подгруппе и роли (все / руководители / участники); внутри каждой группы руководители выводятся первыми, затем остальные участники по алфавиту.
- Длинные списки участников, задач, активности и проблем прокручиваются внутри ограниченных по высоте панелей.
- Карточки подгрупп размещены в горизонтальной прокручиваемой ленте: при добавлении пятой и последующих групп они появляются справа, не переносясь на новую строку.
- Локальное сохранение в браузере через `localStorage`.
- Демо запускается с четырьмя примерами подгрупп и 40 тестовыми участниками (имена «Участник 01–40»), чтобы проверить вид колец и таблиц. Эти записи можно полностью переименовать, изменить или удалить.

**Важно:** демо-режим хранит изменения только в текущем браузере. Разные люди не увидят данные друг друга. Для общей синхронизации нужен проект Supabase (база + вход пользователей), описанный ниже.

## Архитектура

- GitHub Pages — публично размещает статические файлы сайта.
- Supabase — общая PostgreSQL-база и авторизация.
- `config.js` — публичный Supabase Project URL и publishable/anon key. Секретный `service_role` key сюда помещать нельзя.

GitHub Pages публикует HTML/CSS/JavaScript из репозитория; серверную часть он не запускает. Поэтому база и правила доступа вынесены в Supabase.

## Локальный запуск для проверки кнопок

Не открывайте `index.html` двойным щелчком через адрес `file://`: браузер может блокировать загрузку JavaScript-модулей и внешних ресурсов. В обновлённой версии основной скрипт подключён как обычный JavaScript-файл, но для корректной проверки всё равно рекомендуется локальный HTTP-сервер.

В терминале перейдите в папку `project-dashboard/` и выполните:

```bash
python -m http.server 8000
```

Затем откройте `http://localhost:8000/`. Для остановки сервера нажмите `Ctrl+C`.

Если кнопки не реагируют уже на опубликованном сайте, откройте DevTools (F12) → Console, обновите страницу и проверьте ошибки. Во вкладке Network убедитесь, что `app.js`, `styles.css` и `config.js` загружаются со статусом 200.

## Публикация на GitHub Pages

1. Создайте **public repository** на GitHub, например `project-control-center`.
2. Распакуйте архив. Загрузите **содержимое** папки `project-dashboard/` в корень репозитория, чтобы `index.html` лежал прямо в корне. Включите скрытые файлы и папку `.github/workflows/`.
3. Убедитесь, что основная ветка называется `main`.
4. Откройте **Settings → Pages**. В разделе **Build and deployment** обязательно выберите **Source = GitHub Actions**. Ошибка `Get Pages site failed` / `404 Not Found` на шаге `Configure Pages` обычно означает, что GitHub Pages ещё не включён для репозитория или источник публикации не настроен.
5. Убедитесь, что в корне репозитория лежат `index.html`, `app.js`, `styles.css`, `config.js`, а workflow лежит по пути `.github/workflows/pages.yml`. Загрузите именно содержимое папки `project-dashboard/`, а не саму папку целиком.
6. Откройте вкладку **Actions** и повторно запустите workflow (`Re-run all jobs`) либо сделайте новый commit в `main`. Workflow `Deploy static dashboard to GitHub Pages` опубликует сайт.
7. Адрес будет иметь вид `https://ВАШ-ЛОГИН.github.io/ИМЯ-РЕПОЗИТОРИЯ/`.

Для небольших изменений кода можно нажать `.` на странице репозитория, чтобы открыть `github.dev`, внести изменения и сделать commit. Это редактор исходников, а не сервер/хостинг сайта. Публикацию выполняет GitHub Pages workflow после commit в `main`.

## Подключение общей базы Supabase

1. Создайте проект на [supabase.com](https://supabase.com/).
2. В Supabase откройте **SQL Editor**, вставьте содержимое `supabase/schema.sql` и выполните запрос.
3. В **Project Settings → API** скопируйте Project URL и publishable key (или legacy anon key).
4. В `config.js` вставьте их в поля `supabaseUrl` и `supabaseAnonKey`.
5. Сохраните `config.js` в GitHub. Project URL и publishable/anon key предназначены для браузера. Никогда не используйте `service_role` key в клиентском приложении.
6. В Supabase откройте **Authentication → Users** и создайте пользователя-администратора (например, свой университетский email и пароль).
7. Скопируйте UUID этого пользователя из Auth → Users. В SQL Editor выполните, заменив значения:

```sql
insert into public.profiles (user_id, display_name, role)
values ('UUID_ИЗ_AUTH_USERS', 'Имя администратора', 'admin')
on conflict (user_id) do update
set display_name = excluded.display_name, role = 'admin';
```

8. Перезагрузите сайт, нажмите **Войти для синхронизации** и войдите под этим аккаунтом.
9. Добавьте группы, участников и задачи через интерфейс сайта. Они будут записываться в общую базу и автоматически обновляться у открывших сайт посетителей через Supabase Realtime.
10. Чтобы добавить руководителя с правом редактирования своей группы: создайте ему пользователя в Supabase Auth, добавьте строку в `profiles` с ролью `leader` и `team_id` нужной группы. После добавления группы её UUID можно посмотреть в Table Editor → teams. Одной отметки «Руководитель» в списке участников недостаточно для входа в систему — необходима отдельная учётная запись Supabase.

Пример создания профиля руководителя:

```sql
insert into public.profiles (user_id, display_name, role, team_id)
values ('UUID_ПОЛЬЗОВАТЕЛЯ', 'Имя руководителя', 'leader', 'UUID_ГРУППЫ');
```

## Публичность и права

- Сайт и проектная статистика доступны для просмотра любому посетителю.
- Анонимные посетители не могут изменять базу.
- Администратор может менять настройки проекта и группы.
- Руководитель может менять участников, задачи и проблемы своей группы.
- Публичная регистрация не включена: пользователей создаёт администратор в Supabase Auth.

Это важное разделение: **публичный просмотр не означает публичное редактирование**. Иначе любой посетитель мог бы испортить статистику.

## Как рассчитывается вклад на круговых диаграммах

- Задача с `Done` считается выполненной.
- Для участника суммируется вес его выполненных задач в группе.
- Каждый участник получает отдельный сектор кольца. Размер сектора пропорционален суммарному весу задач, назначенных участнику.
- Заполненная цветом часть сектора показывает личный прогресс участника. В автоматическом режиме он рассчитывается как выполненный вес его задач / общий вес назначенных ему задач × 100. Для каждого участника можно переключить расчёт на ручной и задать процент 0–100.
- Процент в центре круга = средневзвешенный прогресс задач группы. Для каждой группы можно отдельно переключить расчёт на ручной и указать процент 0–100.
- Общий процент проекта рассчитывается с учётом прогресса задач, ручных процентов участников и групповых переопределений. Его также можно переключить на ручной и задать от 0 до 100.
- Вес задачи по умолчанию равен 1, но его можно менять в редакторе задачи.
- Общий прогресс проекта автоматически агрегируется по весам задач. При необходимости администратор может переключить проект на ручной процент.

Важно: такой показатель измеряет **учтённые выполненные задачи**, а не объективную личную производительность. Для честного сравнения согласуйте между подгруппами, что считается одной задачей и когда следует менять статус на `Done`.

## Важное о публичности и персональных данных

Публичный сайт и публичная статистика означают, что имена участников, названия задач и история активности доступны посетителям. Перед публикацией согласуйте это с группой. Если не все согласны на открытые имена, используйте имена-псевдонимы или инициалы. Сам репозиторий GitHub Pages также будет публичным.

## Ограничения стартовой версии

- Это стартовая версия для проверки структуры и процесса, а не готовая сертифицированная система.
- Для реального запуска проверьте политики RLS, добавьте тесты доступа и не храните в публичной базе личные или конфиденциальные сведения.
- Чтобы дать участникам возможность самостоятельно менять задачи, нужно создать для них профили Supabase и отдельно настроить правила на редактирование только назначенных им задач. Сейчас редактирование общих данных предназначено администратору и руководителям групп.
- Бесплатный тариф Supabase подходит для учебного прототипа, но может приостанавливать неактивные проекты; перед длительным использованием проверьте актуальные условия тарифа.
